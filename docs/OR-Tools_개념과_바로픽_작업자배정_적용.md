# OR-Tools 개념과 바로픽 MFC 작업자 배정 적용

## 1. OR-Tools란 무엇인가?

**OR-Tools(Operations Research Tools)**는 Google이 개발한 오픈소스 **수학적 최적화(Optimization) 라이브러리**입니다.

여러 선택지 중에서 주어진 조건을 만족하면서 가장 효율적인 결과를 계산하는 도구입니다.

예를 들면 다음과 같은 문제를 해결합니다.

- 작업자 10명에게 피킹 작업 30개를 어떻게 배정해야 할까?
- 배송기사 5명이 배송지 50곳을 어떤 순서로 방문해야 할까?
- 직원들의 휴식시간을 보장하면서 근무표를 어떻게 구성해야 할까?
- 제한된 차량과 인력으로 최대한 많은 배송을 처리하려면 어떻게 해야 할까?

이러한 문제는 조합이 증가할수록 사람이 직접 계산하기 어려워집니다. OR-Tools는 문제를 수학적으로 표현하고 효율적인 해답을 탐색합니다.

- 공식 홈페이지: https://developers.google.com/optimization
- GitHub: https://github.com/google/or-tools

## 2. OR-Tools는 AI인가?

일반적인 딥러닝 AI 모델과는 다릅니다.

| 구분 | AI·딥러닝 모델 | OR-Tools |
|---|---|---|
| 목적 | 예측·분류·생성 | 최적의 의사결정 탐색 |
| 동작 방식 | 데이터로 패턴 학습 | 변수·제약조건·목적함수로 계산 |
| 학습 데이터 | 보통 필요 | 필수 아님 |
| 모델 학습 | 일반적으로 필요 | 필요 없음 |
| 주요 결과 | 예측값·확률 등 | 배정·순서·일정·수량 |
| 대표 사례 | 내일 주문 500건 예측 | 작업자에게 실제 피킹 업무 배정 |

AI 모델이 내일 주문량을 예측한다면, OR-Tools는 실제 발생한 피킹 작업을 누구에게 배정할지 계산합니다.

**AI는 미래를 예측하고, OR-Tools는 주어진 상황에서 좋은 결정을 찾습니다.**

## 3. OR-Tools의 핵심 원리

OR-Tools의 최적화 모델은 대체로 **결정 변수, 제약 조건, 목적 함수**로 이루어집니다.

### 3.1 결정 변수(Decision Variables)

OR-Tools가 실제로 결정해야 할 값입니다.

작업자가 A, B, C이고 피킹 작업이 1, 2, 3이라면 다음과 같은 변수를 둘 수 있습니다.

$$
x_{ij} = \begin{cases}
1 & \text{작업자 }i\text{가 작업 }j\text{를 담당} \\
0 & \text{담당하지 않음}
\end{cases}
$$

작업자 A가 작업 1을 담당하면 `x[A,1] = 1`, 담당하지 않으면 `x[A,1] = 0`입니다.

### 3.2 제약 조건(Constraints)

반드시 지켜야 하는 규칙입니다.

- 각 피킹 작업은 정확히 한 명에게 배정한다.
- 냉동 작업은 냉동 구역 작업이 가능한 사람에게만 배정한다.
- 휴식 중인 작업자에게 신규 작업을 배정하지 않는다.
- 작업자별 처리 가능한 작업량을 초과하지 않는다.
- 이미 시작한 작업은 원칙적으로 재배정하지 않는다.

이러한 필수 조건을 **Hard Constraint(강제 제약 조건)**라고 합니다. 모든 조건을 만족하는 배정이 없으면 최적화 모델은 실행 불가능한 결과를 반환할 수 있으므로 예외 정책이 필요합니다.

### 3.3 목적 함수(Objective Function)

제약을 만족하는 여러 배정 중 어떤 것을 더 좋다고 평가할지 정의합니다.

| 목표 | 의미 |
|---|---|
| 이동 거리 최소화 | 작업자와 상품 LOC 사이의 이동 감소 |
| 마감 지연 최소화 | 배송 마감시간을 넘기는 작업 감소 |
| 작업량 균등화 | 특정 작업자에게 업무가 몰리는 현상 감소 |
| 작업 완료시간 최소화 | 전체 피킹 작업을 최대한 빠르게 종료 |
| 재배정 최소화 | 기존 작업을 불필요하게 변경하지 않음 |

가중치를 사용한 예시:

$$
\text{비용} = \alpha\times\text{이동시간}
+\beta\times\text{지연시간}
+\gamma\times\text{작업량 불균형}
$$

여기서 $\alpha$, $\beta$, $\gamma$는 목표의 상대적인 중요도입니다. OR-Tools는 이러한 비용이 작아지는 해를 찾습니다.

## 4. OR-Tools는 내부적으로 어떻게 계산할까?

OR-Tools는 단일 알고리즘이 아니라 다양한 최적화 도구를 묶은 라이브러리입니다.

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| CP-SAT | 복잡한 제약 조건 아래에서 조합 최적화 | 피킹 배정, 근무 일정 |
| Linear Programming | 선형 수식 기반 최적화 | 비용·자원 배분 |
| Mixed Integer Programming | 정수 및 연속 변수 최적화 | 생산·물류 계획 |
| Assignment | 작업과 담당자 간 배정 문제 | 작업자별 업무 배정 |
| Routing | 이동 경로 및 방문 순서 최적화 | 배송 경로, 피킹 경로 |
| Bin Packing | 제한된 공간·용량에 물건 배치 | 박스·차량 적재 |

### 4.1 CP-SAT이란?

바로픽 작업자 배정에 특히 검토할 만한 최적화 엔진입니다.

- **CP(Constraint Programming):** 여러 변수 사이의 제약 조건을 만족하는 조합을 탐색하는 접근
- **SAT(Boolean Satisfiability):** 참·거짓 조건을 동시에 만족시킬 수 있는지 판단하는 문제

CP-SAT은 이러한 기법과 정수 최적화 기법을 이용해 복잡한 조합 문제를 해결합니다.

예를 들어 작업자 5명, 피킹 작업 20개, 온도대별 자격, 현재 위치, 작업별 소요시간, 배송 마감이 동시에 주어진 상황을 모델링할 수 있습니다.

단, 항상 전역 최적해를 즉시 찾는 것은 아닙니다. 계산 시간을 제한하면 그때까지 찾은 실행 가능한 해를 반환할 수 있으며, 최적성을 증명하지 못할 수 있습니다.

## 5. 예시로 이해하는 작업자 배정

다음 값은 개념을 설명하기 위한 **가상 데이터**입니다.

### 작업자 정보

| 작업자 | 현재 위치 | 가능 작업 |
|---|---|---|
| A | 상온 A구역 | 상온, 냉장 |
| B | 상온 B구역 | 상온 |
| C | 냉장 C구역 | 냉장, 냉동 |

### 신규 피킹 작업

| 작업 | 구역 | 우선순위 |
|---|---|---|
| 작업 1 | 상온 A구역 | 일반 |
| 작업 2 | 상온 B구역 | 일반 |
| 작업 3 | 냉장 C구역 | 긴급 |

### 작업자별 예상 이동시간

| 작업 | A | B | C |
|---|---:|---:|---:|
| 작업 1 | 1분 | 8분 | 6분 |
| 작업 2 | 7분 | 1분 | 8분 |
| 작업 3 | 6분 | 수행 불가 | 1분 |

각 작업을 서로 다른 작업자에게 한 개씩 배정하고 이동시간 합계를 최소화하면:

- 작업자 A → 작업 1 (1분)
- 작업자 B → 작업 2 (1분)
- 작업자 C → 작업 3 (1분)

**총 예상 이동시간: 3분**

이 결과는 설명을 위한 계산 예시이며 실제 OR-Tools 실행 결과는 아닙니다. 실제 운영에는 이동시간 외에도 작업 소요시간, 휴식, 배송 마감, 작업량을 함께 반영해야 합니다.

## 6. 바로픽 WMS에 적용하는 구조

첨부 문서는 OR-Tools를 **피킹 작업자 자동 배정**과 **근무 스케줄 최적화**에 활용하는 방향을 제시합니다. 아래는 그 사용 목적을 바탕으로 한 적용 설계 예시입니다.

```text
OMS (주문 접수·주문 정보)
           │
           ▼
WMS (피킹 작업 생성·재고·작업자 상태 조회)
           │
           ▼
OR-Tools 최적화 엔진
 ├─ 결정 변수 생성
 ├─ 제약 조건 적용
 └─ 목적 함수 최적화
           │
           ▼
작업자별 피킹 배정 후보
           │
           ▼
WMS (최신 상태 재검증·배정 확정·DB 저장)
           │
           ▼
작업자 앱 (배정 확인·피킹 수행)
```

OR-Tools 자체는 주문 조회, DB 저장, 앱 알림을 수행하지 않습니다. 입력된 최적화 문제를 계산해 결과를 반환하는 라이브러리입니다.

| 구성요소 | 담당 역할 |
|---|---|
| OMS | 주문·배송 관련 정보 제공 |
| WMS | 작업 생성, 작업자 상태·LOC 관리 |
| OR-Tools | 제약 조건에 따른 최적화 계산 |
| WMS DB | 배정 결과 저장 및 동시성 제어 |
| 작업자 앱 | 배정 작업 표시 및 수행 상태 전송 |

최적화 계산 중 작업자 상태나 주문 상태가 달라질 수 있으므로 **계산 결과를 그대로 확정하지 말고 WMS에서 최신 상태를 재검증**해야 합니다.

## 7. OR-Tools는 서버인가, 라이브러리인가?

OR-Tools는 기본적으로 **라이브러리**입니다. Elasticsearch·Kafka처럼 별도 서버를 반드시 운영해야 하는 구조가 아닙니다.

| 기술 | 유형 | 별도 서버 필요 여부 |
|---|---|---|
| Elasticsearch | 검색 엔진·서버 | 일반적으로 필요 |
| Kafka | 이벤트 스트리밍 플랫폼 | 브로커 필요 |
| PostgreSQL | 데이터베이스 서버 | 필요 |
| OR-Tools | 최적화 라이브러리 | 필요 없음 |

OR-Tools는 C++로 구현되어 있으며 Java, Python, C#에서도 사용할 수 있습니다.

### 7.1 방식 A — Java WMS에 직접 추가

Spring Boot 기반 WMS에 OR-Tools Java 라이브러리를 추가하여 같은 애플리케이션에서 배정 최적화를 실행합니다.

장점:

- 별도 최적화 서비스 불필요
- 별도 REST 통신 불필요
- 기존 WMS 책임 및 배포 구조 유지

검토사항:

- Java 네이티브 라이브러리 로딩
- Docker 이미지 및 OS 아키텍처 호환성
- 계산 시간 제한 및 자원 격리

### 7.2 방식 B — Python 최적화 서비스 분리

Python에서 OR-Tools를 실행하고 WMS가 REST API 등을 통해 배정 계산을 요청합니다.

장점은 독립적 확장과 배포가 가능하다는 점이며, 단점은 새로운 서비스 운영·통신·장애 처리 부담이 생긴다는 점입니다.

**현재 바로픽처럼 Java/Spring Boot 기반 WMS를 운영하는 개발 단계에서는 방식 A를 우선 권장합니다.**

- Java 시작 가이드: https://developers.google.com/optimization/introduction/java

## 8. 도입 전 중요한 설계 문제

### 8.1 무엇을 배정 단위로 삼을까?

- **주문 단위:** 주문 하나를 작업자 한 명에게 할당
- **피킹 작업 단위:** 온도대·구역별 작업을 각각 할당
- **배치·Wave 단위:** 여러 주문의 피킹 작업을 묶어 할당

상온·냉장·냉동 구역이 나뉘는 MFC에서는 주문 단위보다 **WMS의 실제 피킹 작업 단위**로 최적화하는 것이 유리할 수 있습니다.

### 8.2 언제 다시 계산할까?

| 시점 | 처리 예시 |
|---|---|
| 신규 주문 접수 | 배정 대기 작업 등록 |
| 작업자가 유휴 상태가 됨 | 배정 계산 요청 |
| 긴급 주문 발생 | 우선순위를 반영한 재계산 |
| 지정된 주기 도달 | 미배정 작업 일괄 최적화 |

이미 피킹 중인 작업까지 반복적으로 변경하면 현장 혼란이 생길 수 있으므로 **진행 중인 작업은 원칙적으로 고정**하는 것이 좋습니다.

### 8.3 계산이 오래 걸리면?

CP-SAT에는 계산 시간 제한을 설정할 수 있습니다. 예를 들어 **최대 1초만 탐색**하는 정책을 둘 수 있습니다. 이는 설정 예시이지 성능 보장이 아닙니다.

처리 절차 예시:

1. 유효한 배정 후보가 있으면 해당 결과 활용
2. 실행 가능한 결과가 없으면 규칙 기반 배정으로 전환
3. WMS에서 최신 상태를 재검증한 다음 배정 확정

실시간 피킹 운영에서는 완전한 수학적 최적성보다 **충분히 좋은 결과를 신속하고 안정적으로 만드는 것**이 중요할 수 있습니다.

### 8.4 작업자 수가 적어도 필요한가?

반드시 필요하지는 않습니다. 작업자 3명, 대기 작업 2개 정도라면 단순 규칙이 충분할 수 있습니다.

작업자·작업 수가 늘고 온도대·거리·마감·업무량 조건이 복잡해지면 OR-Tools의 장점이 커질 수 있습니다. 단, 구체적인 적용 기준은 실제 입력 데이터로 배정 품질과 계산 성능을 비교해 결정해야 합니다.

## 9. 바로픽 권장 적용 방향

| 항목 | 권장 방식 |
|---|---|
| 적용 위치 | 기존 WMS 내부 |
| 개발 언어 | Java |
| 라이브러리 | Google OR-Tools |
| 우선 검토 엔진 | CP-SAT |
| 최적화 대상 | 미배정 피킹 작업 |
| 강제 제약 | 작업 자격, 작업 상태, 처리 용량 |
| 최적화 목표 | 마감 준수, 이동·작업시간 최소화, 부하 균등화 |
| 계산 실패 시 | 규칙 기반 배정 |
| 최종 배정 확정 | WMS |
| AI 학습 모델 | 초기에는 불필요 |

복잡한 시간·순서·운영 규칙이 많으면 CP-SAT을 우선 검토하되, 단순한 작업자-작업 매칭이라면 Assignment 또는 Minimum Cost Flow가 더 간단할 수도 있습니다.

**핵심은 라이브러리를 설치하는 것이 아니라 바로픽의 피킹 배정을 어떤 수학적 문제로 정의할 것인지 결정하는 것입니다.**

특히 아래 정책이 중요합니다.

- 한 작업자가 여러 주문을 동시에 피킹할 수 있는가?
- 온도대별 작업을 분리할 것인가?
- 이미 배정된 작업을 언제 변경할 수 있는가?
- 배송 마감 준수와 이동 거리 중 무엇을 우선할 것인가?

이 기준이 정해지면 결정 변수·제약 조건·목적 함수를 구체화하고 Java WMS에 연결할 수 있습니다.
